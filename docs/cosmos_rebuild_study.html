1What COSMOS Is

COSMOS (Curated Organizational System for Metadata and Science) is the curation web application behind NASA's Science Discovery Engine. Curators use it to decide which URLs from crawled NASA web sources get indexed into the SDE — a Sinequa-based search deployment — and with what metadata: title, document type, SMD division, TDAMM astronomy tags.

Think of it as a quality-control checkpoint between a web crawler and a search engine: the crawler dumps in everything it finds; curators write rules ("patterns") to throw out junk, fix titles, and tag content; only the approved, cleaned-up set is promoted to production indexing.

  • Stack: Django 4.2 + PostgreSQL + Celery/SQS + Redis; DRF with server-side DataTables; Bootstrap/jQuery frontend; Docker Compose deploys.
  • Scale: ~24.5k lines of Python across 7 apps (≈12.2k non-migration code in the core app), ~4.7k lines of custom JS, ~3k lines of templates. Collections range from 1 URL to over 100,000; full-text dumps reach ~1.8M records.
  • Activity: 1,300+ merged PRs, latest January 2026. No open-source license is declared — port behavior, not code.

2Core Domain Model

The URL lifecycle

DumpUrlRaw rows from a dev-server crawl: url, scraped title/text, tags
→
DeltaUrlWork-in-progress diff vs. production; carries to_delete tombstones
→
CuratedUrlApproved production set, exported to the Sinequa indexer

Migration (dump → delta): diff each dump row against curated on scraped_title, tdamm_tag, division; create deltas only where different, plus deletion deltas for curated URLs that vanished from the crawl; apply all patterns; clear the dump. Promotion (delta → curated): on "Curated" status, upsert every delta (NULLs are explicit values), delete tombstoned rows, clear deltas. Patterns are not re-applied at promotion — their effects travel as plain field values. The three-table design exists because Sinequa reindexes are expensive and asynchronous: the tool must hold a proposed state for weeks.

The pattern system (the heart of the tool)

PatternEffect
ExcludeMark matching URLs excluded from indexing
IncludeForce-include — always wins over exclude
TitleRewrite title: literal text + {url}/{title}/{collection} + xpath://… extraction from the live page
Document typeAssign Images / Data / Documentation / Software & Tools / Missions & Instruments
DivisionAssign SMD division (Astrophysics, BPS, Earth Science, Heliophysics, Planetary, General)

Patterns match an individual URL or a multi-URL wildcard (* glob → regex). The required behaviors, all documented in the repo's own README_PATTERN_*.md spec files: idempotent application with per-pattern effect tracking; unapply logic (deleting a pattern generates deltas reversing its effects — the next most specific pattern takes over, else the curated value, else NULL); include-over-exclude precedence; and "smallest match set wins" specificity resolution for field-modifying patterns, ties broken by longest pattern string.

Workflow state machines

A 20-state workflow status drives automation on transition: Ready for Engineering generates scraper configs and pushes to GitHub; Indexing Finished on Dev fetches full text; Ready for Curation generates indexer configs; Curated promotes deltas; QC Perfect/Minor appends the collection to the public query config. Eleven transitions post Slack notifications. A parallel 7-state reindexing status tracks the re-crawl loop, and Sinequa's indexer itself polls COSMOS for its next job and reports back through an API endpoint. Auxiliary requirements: manual-overrides-ML paired metadata fields (tdamm_tag_manual / tdamm_tag_ml), required-URL acceptance checks, per-collection comments, and auto-logged status history.

3External Integrations

  • Sinequa, inbound: 9 named server configs; paginated search.query and engine.sql full-text pulls with adaptive batch backoff.
  • Sinequa, outbound configs: XML generation for scraper/indexer/job configs from templates; COSMOS patterns normalized to Sinequa wildcard rules and title/doc-type mappings.
  • Sinequa, outbound URL lists: /curated-urls-api/<folder>/ — the machine-facing product of the whole app: non-excluded URLs as {url, title, document_type, file_extension, tree_root, tdamm_tag}, consumed by a Sinequa C# plugin.
  • GitHub: branch → commit XMLs → PR against the Sinequa config repo; metadata read-back and a DB-vs-GitHub consolidation diff view.
  • Slack webhook notifications; AWS SQS/S3/SES; an external ML inference microservice for TDAMM and division classification with per-tag confidence thresholds and off-peak scheduling.

4Distilled Requirements

Must have — the irreducible core:

R1Named collections with source URL, division, connector type, lifecycle status.
R2Ingest a crawl dump of URLs (+ titles/text/metadata) per collection.
R3Rule-based curation: the five pattern types with idempotency, unapply, include-precedence, and specificity resolution.
R4Diff-based staging: review new / modified / deleted URLs before promoting.
R5Promote to a curated production list; export it in the exact shape the indexer consumes.
R6Generate crawler/indexer configs from templates driven by collection metadata.
R7Workflow status per collection with an auditable history.

Should have:

R8Multi-curator assignment and simple auth.
R9Automated metadata suggestion (doc type, division, TDAMM) preserving manual-overrides-ML semantics.
R10Notifications on state changes (Slack / GitHub).
R11Bulk operations across tens of thousands of URLs with acceptable performance.

Peripheral (candidates to drop): R12 feedback app, environmental-justice app, admin conveniences, DB backup commands, Sinequa dashboards, deployment scaffolding.

5Reimplementation Options

COSMOS is big because it is a multi-curator production web service. The irreducible logic — patterns, diff, promotion, config generation — is on the order of 1–2k lines. An everyday analogy: COSMOS is a full commercial kitchen built to serve one signature dish; the recipe fits on two pages, and the question is how much kitchen you actually need — a food truck (CLI), a home kitchen (small web app), or a personal chef who cooks on request (Claude skill).

Option A — Python CLI engine (cosmos-lite) on SQLite

A pip-installable package: Typer CLI + library API, SQLite/DuckDB store, Jinja2 for the Sinequa XML templates.

cosmos-lite ingest <collection> dump.csv          # R2
cosmos-lite pattern add --type exclude --match "*/legacy/*"
cosmos-lite apply | diff | promote <collection>   # R3, R4, R5
cosmos-lite export <collection> --format urllist|xml
cosmos-lite status <collection> --set curated     # R7

Covers R1–R7 and R11; classification via optional API calls (R9). Drops the web UI and multi-user auth. Roughly 1.5–2.5k lines with a pytest suite that encodes the pattern semantics from the in-repo READMEs. Matches the house preference for Python with tests built in. Weakness: no grid for eyeballing 10k URLs — mitigate with a generated HTML review report or Datasette over the SQLite file.

Option B — Claude Code skill wrapping the engine

A skill whose SKILL.md encodes the curation workflow, with data in a git-tracked folder (collection.yaml, patterns.yaml, curated.parquet, deltas.parquet). The skill drives the Option-A engine and adds what COSMOS needed servers for: Claude classifies content conversationally (R9 with zero infrastructure), drafts patterns by inspecting URL structure — something COSMOS cannot do — and runs QC sampling. Git supplies the audit trail. Single-curator by construction; bulk work stays in scripts so Claude reviews samples and aggregates rather than paging through 100k URLs. Per workspace rules, actually building this goes through the akd_care_design_process; this report is its Phase-1 input.

Option C — Minimal web app (FastAPI + HTMX + SQLite)

One 3–5k-line service reusing the Option-A engine, adding simple auth (R8) and a real curation grid — the one thing CLIs do badly and exactly where COSMOS's bulk lives (the workbench page alone is 2,276 lines of JS). Choose this only if multiple non-technical curators need simultaneous point-and-click access; at that point, trimming COSMOS itself is worth weighing against a rewrite.

Option D — Git-native pipeline (files + CI as the state machine)

No database, no server: URLs as Parquet, patterns as YAML, all in a repo. CI runs apply/diff on push; the pull request is the curation review; merge is promotion; a release tag is "in production". Config XMLs are CI-committed artifacts. Astonishingly little code (engine + ~200 lines of workflow YAML) and PR-native notifications — but curators must live in GitHub, which the SDE team already partly does.

Option E — Assemble from data tools (Datasette / NocoDB)

Point an existing table UI at the SQLite store; scripts do the rest. Fastest browsable UI for near-zero code, but pattern lifecycle logic stays script-side and you inherit another tool's deployment. Worth knowing; rarely the best endpoint.

6Recommendation

Recommended path

Build A, wrap it in B, adopt D's promotion-by-PR when a second curator appears.

Phase 1: the cosmos-lite engine, porting pattern and diff semantics with a pytest suite lifted from COSMOS's own README specs. Phase 2: design the curation skill through the AKD CARE process, with the engine as its tool layer — Claude supplies classification, pattern drafting, and QC sampling. Phase 3 (optional): add the HTMX grid or GitHub-PR flow on the same engine, no rework.

Collapse the 20-state workflow to ~6 states (Backlog → Scraped → Curating → Curated → Config Generated → Live) and keep reindexing as a "needs re-curation" flag until proven insufficient. Skip the feedback app, EJ app, backup tooling, and dashboards entirely.

7Porting Pitfalls

Learned from the code review
  1. Two pattern systems coexist — legacy and delta; XML generation still reads the legacy one. Reimplement only the delta semantics plus the Sinequa wildcard normalizer.
  2. Global URL uniqueness is load-bearing — several unapply paths query by URL without a collection filter. Scope to (collection, url) and fix the queries, or keep the constraint consciously.
  3. Title resolution uses guarded eval() and live HTTP fetches — the language is small; use a plain substitution engine with explicit, batched fetches.
  4. Include/exclude "create" is a toggle (duplicate create = delete) — decide explicitly whether to keep that contract.
  5. Specificity resolution and the 6-case unapply spec are the subtle logic — encode both as tests before implementing.
  6. Avoid the performance trap: COSMOS applies patterns synchronously in model save/delete with per-URL writes; make apply/unapply bulk set operations.
  7. Design in an error surface from day one — the repo's own still-unimplemented ADR admits async failures are invisible to users.
  8. Security hygiene: the current Sinequa client disables TLS verification and puts dev credentials in query strings; don't carry that over.
