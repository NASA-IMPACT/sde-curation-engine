What it is

The engine takes a website from a seed URL to a live entry in the SDE search index. It runs the crawler and the WEB_COSMOS indexer for you and gives you one place to decide what gets indexed and how each page is described. Every collection moves through the same six stages, and the app always shows you the one next thing to do.

Backlogadded, not crawled
Scrapedcrawl loaded
Curatingexclusions → metadata
Curatedapproved set promoted
Test indexindexed, validated
Livein prod, validated

Statuses only move forward when the data supports it. A re-crawl after promotion sends the collection back to Scraped with a ⚠ needs re-curation flag. A failed index is not a curation problem: a failed test index run or validation sends it back to Curated with ⚠ needs re-indexing, and a failed prod validation back to Test index with ⚠ prod not validated. The same ⚠ needs re-indexing chip goes up whenever the curated URLs move past the index — a promote, or an exclude rule applied in place — and comes down when a test index run covers the change.

Three ideas carry the whole app:

  • Three URL sets, always called the same thing. Dump URLs is what the crawler found, raw. Delta URLs is what will change in the curated URLs when you promote. Curated URLs is the approved set; its included rows go to the index. You never edit dump pages. You decide what to do with them.
  • Everything is a rule. Excluding a URL, fixing a title, picking a division: each is a rule you can see, filter by, and delete. Even a one-off edit on a single row is a rule that matches exactly that URL. Rules belong to the collection they were made in; nothing you accept here touches another collection. The only shared input is the global exclude list, and it only ever suggests.
  • Delta URLs are computed, not typed. The engine diffs the dump URLs against the curated URLs and applies your rules. You review the result and promote it.

The quick path

If you only read one section, read this one. Every collection goes through these clicks in this order. The blue Next button in the header always points at the current one.

From seed URL to live index
  1. Add collection on the dashboard: seed URL, name, division, max pages.
  2. Scrape, or load existing if the crawler already has output.
  3. Start curating to compute the delta URLs.
  4. Suggest exclusions, then accept or reject every suggestion.
  5. Continue to metadata.
  6. Suggest metadata, then accept all titles, divisions, and types, or review one by one.
  7. Promote the delta URLs into the curated URLs.
  8. Index to test and wait for validation to pass.
  9. Index to prod and wait for prod validation to pass. The collection is Live.

Signing in: deployed environments require a login. Admins add accounts at /users, everyone changes their own password at /account. Curators can do everything except manage users and delete collections. Every action is recorded under your name.

Walkthrough with screens

The same path, one screen at a time, with what to look at on each.

  1. Find or add the collection on the dashboard

    The home page lists every collection with its status, the dump / delta / curated URL counts, its last job, and the one button for the next step. The filter pane narrows by status, the curating sub-stage, the flags (needs re-curation, needs re-indexing, prod not validated), division, and curator. Press / to jump to search. The jobs strip above the table shows everything running anywhere.

    To add a site, fill in the seed URL, a display name, the division, and a page cap, then press Add collection. The collection id is derived from the seed's host and path, so one host can carry several collections: https://github.com/NASA-AMMOS/ is github.com_nasa-ammos, and a seed at a site's root is just the host. Each row shows the full seed URL under the name.

    The division is yours to give or to leave. Leave it on General — the placeholder meaning “not assigned yet” — and the model suggests a division per page, which you review like any other suggestion. Pick one of the five and it is the division of the whole collection: every URL takes it, the model is never asked for a division at all, and no division suggestions turn up to review. You can change your mind at any time under Overview › Details, to any division — the new one reaches every URL no division rule decides, including URLs already curated, which come back as delta URLs to promote so the change reaches the index. A division rule still overrides it where you need an exception, and going back to General hands the division to the AI again.

  2. Scrape the site, or load a crawl that already exists

    Open the collection and press Scrape. The header shows a spinner and live document counts, with a cancel button next to it. When the crawler already has output for this site, the header also offers or load existing with the date of that output. That ingests it without re-crawling.

    On the deployed environment the crawler is a shared machine that runs one crawl at a time. If someone else's crawl is running, yours shows as queued with how many crawls are ahead. A queued job has no timeout and can legitimately wait a long time.

    When it finishes, the Overview tab's step panel says how many pages were crawled and how many failed, and the Next button becomes Start curating.

  3. Exclusions: decide what must never be indexed

    Press Start curating. The engine computes the delta URLs and opens the Dump URLs tab so you see everything the crawl found before deciding anything; when you have seen enough, open the Curate tab at section 1. Press ✨ Suggest exclusions. It first applies the team's global exclude list, then sends the included delta URLs and titles to the model in batches and asks for exclude globs. On a first pass that is the whole dump; after a re-crawl only what changed, so 90 delta URLs on a 100k-page site cost one call. The button tells you how many URLs and how many calls before you press it; it stays disabled until you have started curating.

    Every suggestion has three options. Accept creates a real exclude rule; the URLs it excludes leave the delta URLs (see excludes are decided by rules). Edit turns the glob into a text box so you can narrow or widen it (say */tag/* to */blog/tag/*) and then Save & accept: the rule is created with your glob and recorded as AI, edited. Reject dismisses it. You can also add an exclude or include rule by hand: a glob with *, or an exact URL (examples in Writing rules by hand). When every suggestion is decided, press Continue to metadata.

    The list shows its first 50 suggestions in place. With more than that, press ⤢ Expand in the section header: the exclusions open on their own page, paginated (25 to 250 per page), with the same accept, edit, reject and accept-all buttons. ⤡ Collapse returns to the whole Curate tab. The Metadata review table expands the same way.

    Know this

    Re-running Suggest exclusions replaces any suggestions you have not yet decided.

    The Metadata section is locked until every exclusion suggestion is decided. If you skipped Suggest exclusions entirely, metadata is allowed with a hint.

  4. Metadata: titles, divisions, and document types

    Press ✨ Suggest metadata. It makes one model call per included delta URL that has not been classified yet, sending the full page text. Each answer carries a title, a division, and a document type, each with a confidence: high means explicit in the text or plain from the rules, medium an inference where another answer is defensible, low a guess. AI titles are free-form: the model is told not to add the collection or site name to them. The model is told the collection's document type when you set one, and the SDE definitions of each document type. Every page gets every field, a title, a division and a document type: when the page does not say, the model gives its best guess with low confidence rather than leaving the field blank. Unless you set the collection's division — then the division is yours, every page already has it, and the model is asked for the title and document type only; it is told your division as context, but never asked to classify one, so no division suggestions come back to review. Answers are saved as they arrive, so cancelling keeps what finished. Calls the provider turns away (rate limits, outages) are tried once more at the end of the run. A URL that still fails shows its error under the URL, the Metadata card links to all of them, and the next Suggest metadata tries them again.

    Duplicate titles. Each page is classified in its own call, so two pages can come back with the same title and the same document type. Suggest metadata flags them and leaves the titles as generated: a ⚠ same title + type ×N chip in the Delta URLs and Curated URLs tables (hover it to see the other pages), a filter (title + doc type shared with another page), and a count on the Metadata card. Pages with the same title but different document types are not duplicates. If there are only a few, edit the titles yourself (✎). Otherwise press ✨ Regenerate duplicate titles: each page is sent back with its full text and the other URLs, and the model writes a new title only, one that says what sets the page apart (a volume, a date range, a target…). The document type is left as it is. The new title replaces the AI suggestion; nothing is applied until you accept it. The row keeps the title it shared, shown as ⚠ was same title + type “…”, with ✎ original to edit that title instead of accepting the new one; the filter AI title regenerated from a duplicate lists these rows. Pending AI suggestions count as if accepted. When some pages of a group have a pending AI title, only those are asked again.

    Under the review bar, a scrolling table lists every URL with a pending suggestion, with the same controls as the Delta URLs table, plus ✓ row / ✕ to decide a whole row at once; Accept all takes every title, division and type in one go. The same rows, with filters, sorting and paging, are under the Delta URLs tab. Each AI badge shows the proposed value and its confidence, with ✓ to accept, ✎ to edit it first (the title opens in an editor prefilled with the suggestion; for division and type the dropdown jumps to the suggested value so you can pick another), and ✕ to dismiss. A value you change before accepting is recorded as AI, edited. Above the table, Review by confidence narrows it to the high, medium or low suggestions, and the field dropdown to titles, divisions or document types. ✓ accept these and ✕ reject these then decide exactly those suggestions, on every page, so you can accept the high ones in bulk and go through the low ones by hand. With any field, a URL is listed when any of its title, division or document type suggestions has that confidence (low + any field lists every page with at least one low suggestion); pick a field to narrow it to that one. A listed row still shows all of its suggestions, including ones of other confidences: ✓ accept these leaves those alone, but ✓ row accepts everything on the row.

    Accept all never undoes a rule you wrote. If you add a rule — a glob, or an edit on one row — after the suggestions are in, the rule is applied straight away, and the fields it decides drop out of every accept-all button. Accepting in bulk would write a newer exact-URL rule right over the rule you just typed, so instead those suggestions stay where they are, marked your rule · not in Accept all, and the buttons say how many they are holding back. Nothing is disabled on the row itself: its ✓ still takes the AI's answer for that one URL, whenever you decide you prefer it. ✕ reject is unaffected — it discards exactly what it says it will.

    Nothing is promoted blank. Promote refuses every delta URL that still has no title, division or document type — and a division of General counts as none, since that is a placeholder, not a division a page belongs to; a suggestion counts only once accepted. Section 3 says how many and which field is missing, and missing title, division or doc type under Delta URLs lists them. Accept the suggestion or set the value by hand, then promote.

    Why the Rules count jumps

    Accepting 22 titles, 22 divisions, and 22 types adds 66 rules, one exact-URL rule per accepted value. That is expected. It is what makes every accepted value visible and reversible in the rules table. Exclude suggestions are globs and stay few.

  5. Promote the delta URLs

    Section 3 of the Curate tab. Promote writes the delta URLs into the curated URLs and marks the collection Curated. If there are no delta URLs, the button reads Mark curated. Recompute delta URLs re-applies the rules without promoting, useful after hand-editing several rules.

    To promote only some of the queue, open Delta URLs, tick the rows (the header box ticks the page) and click Promote selected. The rest stay under review and the collection stays Curating until nothing is left; the rows a rule produced are one click away from its count in the Rules table.

    Know this

    Promoting discards any AI suggestions still undecided on the rows it promotes. The Promote section, and the selection bar under Delta URLs, warn you with the count. Accept or reject them first.

    Curating again after promoting. Once everything is promoted there are no delta URLs, so there is nothing to review and the curation steps sit idle. Two buttons offer the way back, on the Curate tab and on the step-4 panel. Check for changes re-runs the diff against the dump and queues whatever differs — with an unchanged dump it finds nothing, which is the honest answer. Re-curate everything is the deliberate one: every page the rules include goes back into the queue as a modified delta URL, changed or not, and the stages start again at exclusions, so Suggest exclusions, Suggest metadata, the review tables and Promote all have the whole collection to work on again. The curated URLs and the index are untouched until you promote, and a row you leave alone promotes back to exactly the values it already had.

  6. Index to test, validate, then index to prod

    Index to test exports the included curated rows and dispatches an indexing run against the test index. The step-5 panel shows exported, indexed, changed, and deleted counts as it progresses, then the validation result.

    The engine validates on its own. About thirty seconds after the run succeeds it queries the index directly for this collection and compares counts and titles against the curated URLs. The index makes new documents searchable some time after they are written, so a short count is not a failure yet: the engine re-checks every fifteen seconds for up to ten minutes, and the panel reads validating… with how many documents are visible so far. Only once the check passes or the ten minutes run out is the result final. If it lacks access to query the index, it dispatches a second pass of the same export purely to get a fresh validation file. Nothing is re-vectorised on that pass.

    Pass
    Counts match and at least 99% of titles match. Status becomes Test index and Index to prod is enabled.
    Fail
    Back to Curated with the needs re-indexing chip and the mismatches listed. (The chip means one of two things: the last run did not pass, or the curated URLs changed after it — hover it to see which.) Re-index to test, or press Re-validate if you believe the index only needed more time. If the mismatches point at the curation, re-curate first. A test index run that fails outright gets the same chip.

    Index to prod is refused until the latest test run passed. It publishes the test run's vectors to the production index, then runs the same check against prod: the same wait, the same repeated direct query for up to ten minutes, the same counts-and-titles rule. The step-6 panel shows the result, with Re-validate prod beside it.

    Pass
    Status becomes Live and the prod not validated chip goes away.
    Fail
    Back to Test index with the prod not validated chip and the mismatches listed. The published documents stay in prod. Check the prod index, then Re-index to prod, or press Re-validate prod if it only needed more time.
    Cannot check
    Prod has no second pass to fall back to. If the engine cannot read the prod index, the job fails, the collection goes back to Test index with the chip, and the panel reads "not validated". Fix read access, then Re-validate prod.

    Every status transition posts to the team Slack channel with a link.

All three URL tables have the same controls. The Jobs page

/jobs lists every running or queued job across all collections, who started it, and live progress, with the recent history underneath. The dashboard carries a compact version of the same strip.

How rules resolve

Every URL's effective title, division, document type, and included or excluded state is computed from the rules of its own collection; a rule never reaches another collection. When several rules match the same URL:

  • The newest rule wins. For titles, divisions and document types the rule added last decides, whatever its shape: a glob you type by hand takes effect on every URL it matches, including URLs whose value came from an accepted AI suggestion or an earlier edit. Accepting a suggestion afterwards is the newest decision again, on that one URL.
  • Include always beats exclude, however old it is. Use include rules to carve exceptions out of broad excludes; a later exclude never undoes them.
  • No rule, then the curated value, then nothing. Deleting a rule falls back to the next newest rule, then to whatever was last promoted, then to blank. Deleting is the undo.

Title rules are templates. {title} is the scraped title, {url} the URL, {collection} the collection name. A rule with value {title} | GES DISC appends a suffix to every matching page.

Hover any field on the Delta, Curated or Dump URLs to see which rule set it, and who made that rule. The Edited by column summarises it per row: a row whose values all come from accepted AI suggestions reads AI; one you typed or toggled reads SME; both, AI + SME. A broad rule you typed (say a * title template) marks every row it wins as SME, which is correct: you decided it. The match count in the rules table is over the URLs where the rule currently shows: the Delta URLs while there is something to review, the Curated URLs once promoted (an exclude rule's is always over the Dump URLs); clicking it opens that table filtered to the rule. A rule a newer one has beaten everywhere is marked superseded.

Know this

A URL excluded by a rule never reaches the export, the index, or the metadata model. Exclude early to save model calls and review time.

Excludes are decided by rules, not deltas. An excluded URL never waits under Delta URLs: a new page an exclude rule matches is simply left out, and a curated page it matches is flagged excluded in place, so the next index run drops it without a promote. Find excluded URLs under Dump URLs (filter excluded only) and their rules under Rules, where an exclude rule's match count is over the dump. To bring a URL back, delete the rule or press ✓ include: coming back in is a delta URL, reviewed and promoted like any other change. An excluded curated page stays in the Curated URLs list, marked excluded, but leaves the curated count and raises ⚠ needs re-indexing — the index still holds it until the next run.

Writing rules by hand

When no suggestion says what you need, type the rule yourself. Both forms are at the top of the Rules tab, and under their section of the Curate tab: Add an exclude or include rule by hand takes a type and a match; Add a metadata rule by hand takes a type, a match and a value. A rule applies as soon as you add it, is recorded as SME, and is undone by deleting it.

The match: an exact URL or a glob

Without a * the match is an exact URL. It covers every spelling of that page: http or https, with or without www., with or without the trailing slash, with any #fragment. With a * it is a glob, where * stands for any run of characters, including none.

A glob must match the whole URL. Start it with * unless you mean one scheme and host, and end it with * unless you mean "ends here". Only * is special: ?, . and [ are plain characters.

Type exclude keeps matching URLs out of the index; type include is an exception that brings URLs back. An include beats every exclude, however old, so a later exclude never undoes it.

Mistakes that match nothing

/login on its own has no *, so it is an exact URL, and no page's URL is just /login. Write */login*.

A glob without the right scheme or host: https://www.site.gov/docs/* misses https://site.gov/docs/…. Check the URLs in Dump URLs, or start with *.

A match count of 0 after adding a rule almost always means one of the two. Delete the rule and write it again.

"pattern already exists": a collection holds one rule per type and match. To change the value of an existing rule, delete it and add the new one; for a single URL you can also edit its row in a URL table.

Jobs

  • One job per collection at a time. While a job runs, every button that would change that collection is disabled, and any direct request is refused with a conflict. Cancel first if you need to act now.
  • Progress is live. The header chip, the Curate tab, the dashboard row, and the jobs strip show the same progress text and update within seconds.
  • Cancel is safe. A cancelled metadata job keeps every answer that had already arrived. A cancelled scrape leaves the previous crawl in place.
  • Every job ends in succeeded or failed with a reason, shown on the header, the Overview panel, and the Activity tab. Nothing fails silently.
  • An engine restart fails running jobs with the message "engine restarted while job was running". Start them again.

History

Menu → History is the global ledger: every action by anyone on any collection — collections created and deleted, scrapes, rules, URL edits, promotions, index runs, and user administration — newest first, with who did it and when. Filter by user, action name, collection id or detail text; “Older” pages back. Rows are never removed: a deleted collection's history stays, marked deleted, and the delete row records the collection's name and seed URL. A collection's own Activity tab shows the same rows for that collection only.

Working alongside others

Concurrency is per collection, not global. Any number of collections can have jobs running at once. Within one collection, exactly one job runs and edits wait their turn.

  • Different collections never block each other. Assign people to distinct collections and everything is safe.
  • Scrapes queue on the shared crawler. Several people can press Scrape at once. The crawls run one after another. Kick them off early.
  • LLM jobs run in parallel with no shared cap. Each metadata job runs its own pool of concurrent model calls, default twenty-four. Five people classifying at once is over a hundred calls in flight and will hit the provider's rate limit first. Stagger large runs.
  • Job activity is pushed to everyone's browser. You see a colleague's job start and finish live.
  • Edits are not pushed. Header counts catch up within ten seconds, but the URL table and rules list only reload when a job finishes or you refresh. If two people edit the same row of the same collection, the last save wins and nobody is warned. The audit trail records who did what.

Things to know

The list people wish they had read first. Some repeat points from above, gathered in one place.

  • A re-scrape replaces the dump URLs and clears the delta URLs and, if anything was ever promoted, raises the needs re-curation flag. Your rules survive. Undecided suggestions do not.
  • Three different warnings, three different fixes. Needs re-curation means the crawl changed under what you promoted: Start curating. Needs re-indexing means the test index did not check out: Re-index to test or Re-validate. Prod not validated means prod did not check out: Re-validate prod or Re-index to prod. The last two are read off the latest index run, so they only go away when a run passes; promoting, recomputing, or a passing test run never hides a prod problem.
  • "validating…" is not a result. Right after an index run, the index may show only some of the documents. Wait for pass or fail before acting.
  • When pages disappear from the crawl. Say the first crawl found 100 dump URLs and the next one 90. Start curating lists the 10 as removed delta URLs. Promote drops them from the curated URLs, and the next index run deletes them from the index. That is the right outcome for pages a site took down. It is the wrong outcome for a crawl that stopped early, so Promote warns you when a large share of the curated URLs vanished at once: re-scrape instead. To keep a page out of the index while it is still on the site, exclude it; that is the "delete from the index" action.
  • An identical re-crawl returns straight to Curated. Recompute never demotes a collection when nothing changed.
  • Modified includes "text changed". Each page carries a hash of its text. A page whose title and metadata did not move but whose body did shows as modified with a text changed badge, and Suggest metadata re-classifies it. Pages promoted before this existed compare as unchanged the first time.
  • The curated URLs keep their text. Promote copies each page's text from the dump onto its curated row, next to the hash, and an index run ships the curated rows alone. A later re-scrape replaces the dump but not what was approved, so the curated URLs are the source of truth for the next cycle. The Text column on the Curated URLs table is the size of that text; a dash means the row was promoted before the engine kept it, and the next promote fills it.
  • Max pages caps the crawl. If the Dump URLs count sits exactly at the cap, the site is bigger than the crawl. Raise the cap and re-scrape.
  • The Curator filter means who created the collection, not who is working on it. There is no assignment field.
  • The manual status override still obeys the data. Advanced › Set status will not put a collection in Scraped without a crawl, or in Curated with delta URLs outstanding.
  • Suggest exclusions sees URLs and titles only. It cannot know what a page says. Suggest metadata reads the whole page and never truncates it. A page beyond the model's window fails that single URL, shows the error on its row, and is retried on the next run.
  • The prompts are inspectable. Both suggestion cards have a "Show the prompt" toggle. If suggestions look off, read what the model was asked.
  • A malformed model reply fails the job and writes nothing. A bad API key or model name aborts after ten consecutive errors. Per-URL failures never abort.
  • Validation waits on purpose. The thirty-second pause after a test run is the index refresh window, not a stall.
  • Prod indexing is gated on the latest test run. A new test run after a passed one resets the gate until it passes too.
  • CSV export follows your filters. The download on each URL tab contains exactly the rows you are looking at.
  • Old links still work. Links to the previous curate page, and set=deltas links, redirect into the Delta URLs tab.
  • Delete is admin only and permanent. It removes the collection, its crawl, its rules, its runs and its history from the engine. The audit ledger keeps the row naming it, and nothing is removed from S3 or the index — a deleted collection's documents stay indexed.
